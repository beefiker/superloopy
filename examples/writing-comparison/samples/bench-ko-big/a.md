# 설정 동기화 서비스 전환 검토

## 1. 개요

이 문서는 각 서비스가 개별 설정 파일로 관리하는 현재 방식을 중앙 설정 동기화 서비스로 전환하는 안을 검토합니다. 전환 배경이 되는 현재 구조의 문제, 전환 후 달라지는 동작, 단계별 적용 일정, 운영 적용 후 확인할 항목을 함께 다룹니다.

전환의 핵심은 두 가지입니다. 첫째, 설정의 저장 위치를 파일에서 데이터베이스 테이블로 옮깁니다. 둘째, 설정 변경을 각 서비스에 전달하는 일은 프록시가 맡아, 서비스 코드는 수정하지 않고 전환을 마칩니다.

---

## 2. 현재 상황

### 2.1 현재 구조

지금은 12개 서비스가 각자 `config.yaml`을 복사해서 씁니다. 설정값 하나가 바뀌면 그 값을 쓰는 모든 서비스의 파일을 각각 갱신해야 하고, 이 과정에서 일부 서비스만 갱신되는 일이 생길 수 있습니다.

### 2.2 발생한 문제

| 항목 | 수치 |
| --- | --- |
| 설정 불일치로 인한 장애 (지난 분기) | 4건 |
| 평균 복구 시간 | 38분 |

지난 분기에 설정 불일치로 인한 장애가 4건 있었고, 평균 복구 시간은 38분이었습니다. 건수 자체는 크지 않아 보이지만, 복구에 평균 38분이 걸렸다는 것은 원인 파악과 수정 적용에 그만큼 시간이 든다는 뜻입니다. 설정값이 12곳에 흩어진 구조에서는 어느 서비스의 어떤 값이 어긋났는지 찾는 데만도 시간이 걸립니다.

### 2.3 현재 동기화 워커의 동작 문제

현재 동기화 워커에는 두 가지 문제가 있습니다.

- 저장소 연결이 끊기면 이전 값을 그대로 쓰며, 경보를 내지 않습니다. 동기화가 멈춘 상태여도 외부에서는 알 수 없습니다. 연결이 복구되지 않은 채 시간이 흐르면 각 서비스는 낡은 설정으로 계속 동작하고, 운영자는 문제가 표면화된 뒤에야 상황을 알게 됩니다.
- 잘못된 형식의 값은 무시됩니다. 걸러내기는 하지만 그 사실이 드러나지 않아, 설정을 바꿨다고 생각한 쪽과 실제 적용된 값이 어긋날 수 있습니다.

이 두 동작 때문에 설정 불일치가 늦게 드러나고 복구도 그만큼 늦어집니다.

---

## 3. 전환 후 구조

### 3.1 설정 저장 방식

전환 후 모든 설정은 `settings` 테이블에 두고, 스키마는 `schemas/settings.v2.json` 파일을 기준으로 합니다. 설정이 테이블 하나에 모이므로 어떤 값이 지금 유효한지 확인할 지점도 하나로 고정됩니다.

### 3.2 변경 전달 경로

프록시가 설정 변경 이벤트를 각 서비스에 전달하며, 서비스 코드는 수정하지 않습니다. 12개 서비스를 각각 고칠 필요가 없어 서비스별 개발·검증 부담 없이 전환을 진행할 수 있습니다.

### 3.3 설정 읽기 시점

각 서비스는 기동 시 설정을 한 번 읽고, 이후에는 변경 이벤트를 받을 때만 다시 읽습니다. 주기적으로 반복 조회하지 않으므로 불필요한 조회가 없고, 설정이 반영되는 시점도 명확히 구분됩니다.

### 3.4 동기화 작업의 성질

동기화는 같은 설정을 여러 번 적용해도 결과가 같습니다. 그리고 일시적 연결 오류는 재시도로 처리합니다. 결과가 달라지지 않으므로 재시도가 안전하고, 이벤트가 중복 전달되거나 재시도가 여러 차례 이뤄져도 최종 상태는 같습니다.

### 3.5 스키마 검증 실패 시 동작

전환 후에는 스키마 검증에 실패하면 이전 설정을 유지하고 오류 로그를 남깁니다. 현재 워커가 잘못된 형식의 값을 무시하던 것과 달리, 검증 실패 사실이 로그에 남습니다. 이전 설정을 유지하므로 잘못된 값이 그대로 적용되지는 않습니다.

### 3.6 배포 시 동작

배포 시 워커는 진행 중인 동기화를 마친 뒤 종료됩니다. 동기화가 중간에 끊긴 상태로 워커가 내려가지 않아, 배포가 부분 적용 상태를 만들 가능성이 줄어듭니다.

### 3.7 현재 방식과의 비교

| 항목 | 현재 | 전환 후 |
| --- | --- | --- |
| 설정 저장 위치 | 12개 서비스가 각자 `config.yaml` 복사 | `settings` 테이블 |
| 스키마 기준 | 없음 | `schemas/settings.v2.json` |
| 변경 전달 | 각 서비스 파일을 개별 갱신 | 프록시가 변경 이벤트 전달 |
| 서비스 코드 수정 | | 수정하지 않음 |
| 설정 읽기 | | 기동 시 1회 + 변경 이벤트 수신 시 |
| 저장소 연결 끊김 시 | 이전 값 사용, 경보 없음 | 일시적 연결 오류는 재시도 처리 |
| 잘못된 형식의 값 | 무시 | 이전 설정 유지 + 오류 로그 |
| 배포 시 워커 | | 진행 중 동기화 완료 후 종료 |
| 변경 이력 | 없음 | `settings_history` 테이블, 90일 보관 |

---

## 4. 변경 경로와 이력 관리

### 4.1 변경 창구의 단일화

설정 변경은 관리 콘솔에서만 합니다. 변경 경로가 하나뿐이라 누가 언제 어떤 값을 바꿨는지가 흩어지지 않습니다. 파일을 직접 고치던 기존 방식에서는 변경 주체와 시점을 추적하기 어려웠습니다.

### 4.2 변경 이력

변경 이력은 `settings_history` 테이블에 90일 보관합니다. 장애가 나면 그 시점 전후의 설정 변경 내역을 확인할 수 있어 원인 파악 시간이 줄어듭니다. 앞서 적은 평균 복구 시간 38분을 줄이는 데도 이력 조회가 도움이 됩니다.

---

## 5. 단계별 전환 계획

전환은 두 단계로 나눠 진행합니다.

| 단계 | 대상 | 적용 환경 | 일정 |
| --- | --- | --- | --- |
| 1단계 | 결제, 알림 서비스 | 스테이징 | 2026-10-15 |
| 2단계 | 나머지 10개 서비스 | 운영 | 2026-11-05 |

### 5.1 1단계 스테이징 적용(결제·알림)

1단계에서는 결제와 알림 두 서비스를 2026-10-15에 스테이징 환경에 적용합니다. 두 서비스로 범위를 좁혀 스테이징에서 먼저 확인하므로, 문제가 나와도 영향 범위가 제한됩니다.

### 5.2 2단계 운영 적용(나머지 10개 서비스)

2단계에서는 나머지 10개 서비스를 2026-11-05에 운영 환경에 적용합니다. 1단계와 2단계 사이에는 약 3주 간격이 있고, 이 기간에 1단계 결과 확인과 2단계 사전 점검을 합니다.

---

## 6. 확인 항목

전환 중과 이후에 확인할 항목은 세 가지입니다.

### 6.1 운영 적용 직후 모니터링

운영 적용일(2026-11-05)부터 동기화 실패 건수와 경보 발생 여부를 모니터링합니다. 현재 워커는 저장소 연결이 끊겨도 경보를 내지 않으므로, 전환 후 경보가 실제로 발생하는지 확인해야 합니다. 실패 건수와 경보 발생 여부를 함께 봐야 동기화 상태를 제대로 판단할 수 있습니다.

### 6.2 1단계 불일치 발견 시 롤백

1단계에서 불일치가 나오면 `config.yaml` 복사 방식으로 롤백하고 원인을 기록합니다. 기존 방식으로 되돌릴 경로가 준비되어 있어 1단계에서 문제가 확인되더라도 대응할 수 있습니다. 원인 기록은 2단계 진행 여부를 판단하는 근거가 됩니다.

### 6.3 2단계 전 설정값 대조

2단계 전에는 12개 서비스 설정값을 `settings` 테이블과 반드시 대조해야 합니다. 각 서비스가 지금 쓰는 값과 테이블에 저장된 값이 일치하는지 확인하는 절차입니다. 지난 분기 장애 4건의 원인도 설정 불일치였습니다.

### 6.4 확인 항목 정리

| 시점 | 확인 항목 | 조치 |
| --- | --- | --- |
| 1단계 진행 중 | 불일치 발생 여부 | `config.yaml` 복사 방식으로 롤백, 원인 기록 |
| 2단계 이전 | 12개 서비스 설정값과 `settings` 테이블 비교 | 대조 후 진행 |
| 운영 적용일(2026-11-05)부터 | 동기화 실패 건수, 경보 발생 여부 | 지속 모니터링 |

---

## 7. 미결 사항

서비스별 예외 설정 처리 방식은 2단계 전에 논의해 결정해야 합니다. 아직 결정되지 않았고, 2단계 운영 적용(2026-11-05) 전에 결론이 필요합니다. 1단계 스테이징 적용(2026-10-15)과 2단계 사이 기간에 논의하는 것이 일정상 맞습니다. 나머지 10개 서비스를 운영에 적용하기 전에 처리 방식이 정해져 있어야 해서, 논의 일정을 미리 잡을 항목으로 따로 표시해 두었습니다.

---

## 8. 정리

1. 12개 서비스가 각자 복사해 쓰던 `config.yaml`을 `settings` 테이블 하나로 모으고, `schemas/settings.v2.json`을 스키마 기준으로 삼습니다.
2. 프록시가 변경 이벤트를 전달하므로 서비스 코드는 그대로 둡니다.
3. 지금은 연결이 끊겨도 경보가 없고 잘못된 형식의 값이 무시되지만, 전환 후에는 검증 실패 시 이전 설정을 유지하며 오류 로그를 남깁니다.
4. 같은 설정을 여러 번 적용해도 결과가 같으므로 일시적 연결 오류는 재시도로 처리할 수 있습니다.
5. 관리 콘솔로 변경 창구를 단일화하고, `settings_history` 테이블에 90일간 이력을 보관합니다.
6. 결제·알림 서비스를 2026-10-15 스테이징에 먼저 적용하고, 나머지 10개 서비스를 2026-11-05 운영에 적용합니다.
