# 설정 동기화 서비스 전환 검토

## 1. 개요

12개 서비스가 각자 관리하는 설정 파일 방식을 중앙 설정 동기화 서비스로 전환하는 안을 검토한 문서입니다. 현재 구조의 문제, 전환 후 동작, 단계별 일정, 확인 항목, 미결 사항을 다룹니다.

전환의 축은 두 가지입니다.

1. 설정 저장 위치를 파일에서 데이터베이스 테이블로 옮긴다.
2. 변경 전달을 프록시가 맡아, 서비스 코드는 수정하지 않고 전환을 끝낸다.

---

## 2. 현재 상황

### 2.1 구조

12개 서비스가 각자 `config.yaml`을 복사해 사용합니다. 값 하나가 바뀌면 그 값을 쓰는 모든 서비스의 파일을 각각 갱신해야 하고, 그 과정에서 일부만 갱신되는 상태가 생깁니다.

### 2.2 발생한 문제

지난 분기 설정 불일치로 인한 장애가 4건, 평균 복구 시간은 38분이었습니다. 건수보다 복구 시간이 문제입니다. 설정값이 12곳에 흩어진 구조에서는 어느 서비스의 어떤 값이 어긋났는지 찾는 데만 시간이 듭니다.

### 2.3 현재 동기화 워커의 동작

- **저장소 연결이 끊기면 이전 값을 그대로 쓰고, 경보를 내지 않습니다.** 동기화가 멈춰도 바깥에서는 알 수 없습니다. 연결이 복구되지 않은 채 시간이 흐르면 각 서비스는 낡은 설정으로 계속 돌고, 운영자는 문제가 표면화된 뒤에야 알게 됩니다.
- **잘못된 형식의 값은 무시합니다.** 걸러내기는 하지만 그 사실이 어디에도 남지 않습니다. 설정을 바꿨다고 생각한 쪽과 실제 적용된 값이 어긋납니다.

이 두 가지가 2.2의 장애 4건과 복구 시간 38분의 구조적 배경입니다.

---

## 3. 전환 후 구조

| 항목 | 현재 | 전환 후 |
| --- | --- | --- |
| 설정 저장 위치 | 12개 서비스가 각자 `config.yaml` 복사 | `settings` 테이블 |
| 스키마 기준 | — | `schemas/settings.v2.json` |
| 변경 전달 | — | 프록시가 변경 이벤트 전달 |
| 서비스 코드 수정 | — | 없음 |
| 설정 읽기 | — | 기동 시 1회 + 변경 이벤트 수신 시 |
| 저장소 연결 끊김 | 이전 값 사용, 경보 없음 | 일시적 연결 오류는 재시도 |
| 잘못된 형식의 값 | 무시 | 이전 설정 유지 + 오류 로그 |
| 배포 시 워커 | — | 진행 중 동기화 완료 후 종료 |
| 변경 이력 | — | `settings_history` 테이블, 90일 보관 |

(— 는 현재 구조에서 별도로 정의된 동작이 없다는 뜻입니다.)

### 3.1 저장과 스키마

모든 설정은 `settings` 테이블에 두고, 스키마는 `schemas/settings.v2.json`을 기준으로 합니다. 현재 유효한 값을 확인할 지점이 한 곳으로 고정됩니다.

### 3.2 변경 전달

프록시가 설정 변경 이벤트를 각 서비스에 전달하고, 서비스 코드는 수정하지 않습니다. 이번 설계의 핵심입니다. 12개 서비스를 각각 손댈 필요가 없으므로 서비스별 개발·검증 부담 없이 전환합니다.

### 3.3 읽기 시점

각 서비스는 기동 시 설정을 한 번 읽고, 이후에는 변경 이벤트를 받을 때만 다시 읽습니다. 주기적 반복 조회가 없고, 반영 시점이 이벤트 단위로 구분됩니다.

### 3.4 멱등성과 재시도

동기화 작업은 같은 설정을 여러 번 적용해도 결과가 같습니다(멱등). 일시적 연결 오류는 재시도로 처리합니다. 멱등성이 전제이므로 이벤트가 중복 전달되거나 재시도가 반복되어도 최종 상태는 같습니다.

### 3.5 검증 실패와 배포

스키마 검증에 실패하면 이전 설정을 유지하고 오류 로그를 남깁니다. 현재 워커가 잘못된 값을 기록 없이 무시하던 것과 달라지는 지점입니다. 배포 시 워커는 진행 중인 동기화를 마친 뒤 종료하므로, 배포가 부분 적용 상태를 만들 가능성이 줄어듭니다.

---

## 4. 변경 경로와 이력

설정 변경은 관리 콘솔에서만 합니다. 경로가 하나로 제한되므로 누가 언제 어떤 값을 바꿨는지가 흩어지지 않습니다.

변경 이력은 `settings_history` 테이블에 90일 보관합니다. 장애 시 해당 시점 전후의 변경 내역을 바로 조회할 수 있어, 평균 38분이던 복구 시간을 줄이는 데 직접 작용합니다.

---

## 5. 단계별 전환 계획

| 단계 | 대상 | 적용 환경 | 일정 |
| --- | --- | --- | --- |
| 1단계 | 결제, 알림 서비스 | 스테이징 | 2026-10-15 |
| 2단계 | 나머지 10개 서비스 | 운영 | 2026-11-05 |

1단계는 두 서비스로 범위를 좁혀 스테이징에서 먼저 확인하므로, 문제가 나와도 영향 범위가 제한됩니다. 두 단계 사이 약 3주 동안 1단계 결과 확인과 2단계 사전 점검을 진행합니다.

---

## 6. 확인 항목

### 6.1 운영 적용 첫날부터 모니터링

동기화 실패 건수와 경보 발생 여부를 함께 봅니다. 현재 워커가 연결 끊김에 경보를 내지 않는 만큼, 전환 후 경보가 실제로 올라오는지 확인하는 것이 첫날 점검의 핵심입니다.

### 6.2 1단계 불일치 발견 시 롤백

불일치가 나오면 `config.yaml` 복사 방식으로 롤백하고 원인을 기록합니다. 기록한 원인이 2단계 진행 여부를 판단하는 근거가 됩니다.

### 6.3 2단계 전 설정값 대조

12개 서비스의 설정값을 `settings` 테이블과 비교합니다. 지난 분기 장애 4건의 원인이 설정 불일치였으므로, 운영 적용 전 대조는 선행 조건입니다.

---

## 7. 미결 사항

**서비스별 예외 설정 처리 방식** — 2단계 전에 논의해 결정해야 합니다.

2단계 운영 적용일은 2026-11-05이고, 1단계 스테이징 적용일은 2026-10-15입니다. 그 사이 3주가 논의 기간입니다. 나머지 10개 서비스를 운영에 올리기 전에 처리 방식이 정해져 있어야 하므로, 지금 논의 일정을 잡아 두는 편이 좋습니다.

---

## 8. 정리

1. **설정 원본 단일화** — 12개 서비스가 복사해 쓰던 `config.yaml`을 `settings` 테이블로 모으고, `schemas/settings.v2.json`을 스키마 기준으로 삼습니다.
2. **서비스 코드 수정 없는 전환** — 프록시가 변경 이벤트를 전달합니다.
3. **실패 상황의 가시화** — 검증 실패 시 이전 설정을 유지하고 오류 로그를 남깁니다.
4. **안전한 재시도** — 동기화가 멱등하므로 일시적 연결 오류는 재시도로 처리합니다.
5. **변경 경로와 이력 정리** — 관리 콘솔로 창구를 단일화하고, `settings_history`에 90일 보관합니다.
6. **단계적 적용** — 결제·알림을 2026-10-15 스테이징에, 나머지 10개를 2026-11-05 운영에 적용합니다.
