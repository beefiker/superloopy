# 설정 동기화 서비스 전환 검토

**문서 상태:** 검토용 초안
**대상 범위:** 개별 `config.yaml`을 사용하는 12개 서비스 전체
**전환 방식:** 중앙 `settings` 테이블 + 프록시 기반 변경 이벤트 전달(서비스 코드 무수정)
**일정:** 1단계 2026-10-15 스테이징 / 2단계 2026-11-05 운영

---

## 1. 요약

12개 서비스가 각자 복사해 쓰는 `config.yaml` 방식을, 중앙 `settings` 테이블과 프록시 기반 이벤트 전달 구조로 바꾸는 안건입니다.

검토 배경은 지난 분기의 **설정 불일치 장애 4건**과 **평균 복구 시간 38분**입니다. 복사본이 서비스마다 존재하는 구조에서는 어느 복사본이 최신인지 판별하는 데 시간이 들고, 그만큼 복구가 지연됩니다.

전환 후 구조의 핵심은 네 가지입니다.

1. **단일 저장 위치** — 모든 설정은 `settings` 테이블
2. **단일 형식 기준** — `schemas/settings.v2.json`
3. **프록시 전달** — 프록시가 변경 이벤트를 전달하고 서비스 코드는 수정하지 않음
4. **단일 변경 창구** — 관리 콘솔에서만 변경, 이력은 `settings_history`에 90일 보관

현재 워커의 두 동작(연결 단절 시 이전 값 유지·경보 없음, 잘못된 형식의 값 무시)은 전환 후 **검증 실패 시 이전 설정 유지 + 오류 로그 기록**으로 대체됩니다.

미결 사항은 **서비스별 예외 설정 처리 방식** 하나이며, 2단계 전에 결정해야 합니다.

## 2. 현황 진단

### 2.1 현재 구조

12개 서비스가 각자 `config.yaml`을 복사해 사용합니다. 실행 시점에는 서비스 수만큼의 복사본이 존재합니다.

- **복사본 수 = 서비스 수**: 동일 항목에 대해 최대 12개 값이 동시에 존재할 수 있습니다.
- **일치는 보장이 아니라 확인 대상**: 복사 방식에서는 모든 복사본이 같다는 보장이 없고, 비교해야 알 수 있습니다.
- **변경 전파 = 복사 작업**: 설정 변경은 여러 위치의 파일을 각각 갱신하는 일입니다.

### 2.2 지난 분기 지표

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 설정 불일치 장애 | 4건 | 지난 분기 집계 |
| 평균 복구 시간 | 38분 | 위 4건의 평균 |
| 대상 서비스 수 | 12개 | 설정 복사본 보유 |

- 원인이 "설정 불일치"로 분류되었다는 것은, 값 자체의 오류와 별개로 **값이 서로 달라졌다는 사실**이 원인으로 지목되었다는 뜻입니다.
- 38분은 평균값이므로 개별 장애의 분포나 최댓값은 추정할 수 없습니다. "모든 장애가 38분 내외"로 읽지 않아야 합니다.
- 전환 효과는 위 두 지표를 비교 기준으로 삼을 수 있습니다. 목표 수치는 주어지지 않았으므로 별도 합의가 필요합니다(**확인 필요**).
- 4건이 각각 어떤 서비스·어떤 항목에서 발생했는지는 문서에 없습니다. 원인 분석에는 별도 자료가 필요합니다(**확인 필요**).

### 2.3 현재 워커의 동작 특성

| 상황 | 현재 동작 | 운영 관점의 함의 |
| --- | --- | --- |
| 저장소 연결 단절 | 이전 값 유지 | 서비스는 계속 동작하므로 표면상 정상으로 보임 |
| 저장소 연결 단절 | 경보 없음 | 단절 사실이 운영자에게 전달되지 않음 |
| 잘못된 형식의 값 유입 | 해당 값 무시 | 무시되었다는 사실이 드러나지 않음 |

두 동작의 공통점은 실패가 외부로 신호를 내보내지 않는다는 점입니다. 문제 감지 시점이 실제 발생 시점보다 늦어집니다. 또 일부 서비스에서만 값 갱신이 안 되는 상황은 곧 서비스 간 설정 차이로 이어집니다.

여기서 전환 설계의 요구사항이 나옵니다. **실패가 기록으로 남아야 한다**는 것이고, 이는 3.4절의 검증 실패 동작으로 연결됩니다. 위 동작은 결함으로 단정하지 않고 명시된 동작으로 기술했습니다.

## 3. 전환 후 목표 구조

### 3.1 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| `settings` 테이블 | 모든 설정을 보관하는 단일 위치 |
| `schemas/settings.v2.json` | 설정 형식의 기준 스키마 |
| 프록시 | 설정 변경 이벤트를 각 서비스에 전달 |
| 각 서비스 | 기동 시 1회 읽기, 이후 변경 이벤트 수신 시에만 재읽기 |
| 관리 콘솔 | 설정 변경의 유일한 창구 |
| `settings_history` 테이블 | 변경 이력 90일 보관 |
| 동기화 워커 | 멱등, 재시도, 배포 시 진행분 완료 후 종료 |

### 3.2 단일 저장 위치: `settings` 테이블

복사본이 여러 개인 구조에는 무엇이 기준값인지 판정할 지점이 없습니다. 저장 위치를 하나로 모으면 값 비교의 기준이 정해지고, 값이 바뀌는 위치가 한 곳이므로 추적 범위가 줄어듭니다. 2단계 선행 조건인 "12개 서비스 설정값을 `settings` 테이블과 비교"도 단일 기준 테이블이 있어야 성립합니다.

**주의점**

- 저장 위치를 모으는 것과 각 서비스가 그 값을 반영했는지는 별개입니다. 반영 여부는 6절의 확인 절차로 검증합니다.
- 서비스별로 값이 달라야 하는 설정의 처리 방식은 **미결**입니다(9절).

### 3.3 단일 형식 기준: `schemas/settings.v2.json`

현재도 형식 판정은 이루어지고 있으나 결과가 드러나지 않습니다. 기준 파일을 명시하면 검증 통과·실패의 판단 근거가 파일 하나로 특정되고, 스키마 변경 대상과 검증 실패 시 동작의 정의 대상이 분명해집니다.

**절차(권장)**

1. 관리 콘솔로 설정 변경 요청이 들어옵니다.
2. 대상 값을 `schemas/settings.v2.json` 기준으로 검증합니다.
3. 통과하면 반영, 실패하면 이전 설정 유지 + 오류 로그 기록.

**주의점**

- 스키마 파일의 버전 관리와 변경 승인 절차는 주어지지 않았습니다. 파일명이 `v2`이므로 이전 버전이 있을 수 있으나, 관계와 마이그레이션 방식은 **확인 필요**입니다.
- 스키마에 정의되지 않은 항목의 처리는 예외 설정 처리 방식(미결)과 겹칩니다. 2단계 전 논의에서 함께 다루는 편이 낫습니다.

### 3.4 전달 경로: 프록시 기반 이벤트 전달

12개 서비스에 각각 설정 구독 로직을 넣으면 개발·검증 비용이 서비스 수만큼 늘어납니다. 이 전환에서는 프록시가 변경 이벤트를 전달하고 서비스 코드는 수정하지 않습니다.

| 항목 | 프록시 방식의 성격 |
| --- | --- |
| 서비스 코드 변경 | 없음 |
| 이벤트 전달 주체 | 프록시 |
| 전환 단위 | 서비스별 코드가 아닌 전달 계층 |
| 회귀 위험 위치 | 서비스 내부 로직보다 전달 계층 |

**주의점**

- 서비스 코드를 고치지 않는다는 것은 프록시가 단일 경유 지점이 된다는 뜻입니다. 전달 계층의 동작이 전체에 영향을 미치므로 단계적 적용(5절)과 모니터링(6절)이 중요합니다.
- 프록시 배치 형태, 이벤트 프로토콜, 전달 재시도 정책의 세부는 **확인 필요**입니다. 재시도는 "일시적 연결 오류는 재시도로 처리"라는 원칙만 주어져 있습니다.

### 3.5 검증 실패 시 동작

| 상황 | 현재 | 전환 후 |
| --- | --- | --- |
| 잘못된 형식의 값 | 무시됨 | 검증 실패 → 이전 설정 유지 + 오류 로그 |
| 저장소 연결 단절 | 이전 값 유지, 경보 없음 | 경보 발생 여부를 모니터링 항목으로 확인 |

이전 설정을 유지하는 방향은 현재와 같고, **오류 로그가 남는다는 점이 차이**입니다. 문제의 존재가 기록으로 드러나므로 사후 추적이 가능해집니다.

단 **오류 로그와 경보는 구분해야 합니다.** 주어진 사실은 "오류 로그를 남긴다"이며, 로그가 경보로 이어지는지는 명시되어 있지 않습니다(**확인 필요**). 운영 첫날부터 경보 발생 여부를 모니터링하는 항목이 있으므로(6절), 로그–경보 연결은 실제 관찰로 점검합니다.

## 4. 동기화 동작 원칙

### 4.1 멱등성

같은 설정을 여러 번 적용해도 결과가 같습니다. 따라서 재시도에 부작용 우려가 없고, 중복 이벤트가 와도 최종 상태가 같으며, "다시 적용해 본다"가 유효한 복구 수단이 됩니다.

멱등성은 결과가 같다는 보장이며 적용이 항상 성공한다는 보장은 아닙니다. 검증 실패와 연결 오류는 별도 경로로 처리됩니다(3.5절, 4.2절).

### 4.2 재시도

일시적 연결 오류는 재시도로 처리합니다. 멱등성에 의해 재시도로 인한 결과 변화는 없습니다.

**주의점**

- 재시도 횟수·간격·백오프·최종 실패 시 처리는 주어지지 않았습니다. 구현 시 합의가 필요합니다(**확인 필요**).
- 일시적 오류와 지속적 장애의 구분 기준도 명시되어 있지 않습니다. 운영 첫날부터 수집하는 동기화 실패 건수(6절)가 판단 자료가 됩니다.
- 현재 워커가 연결 단절 시 경보를 내지 않는 점을 고려하면, 재시도 처리와 실패 가시화를 함께 확인해야 합니다.

### 4.3 검증 실패 처리 원칙

| 원칙 | 내용 | 의도 |
| --- | --- | --- |
| 보수적 적용 | 검증 실패 시 이전 설정 유지 | 잘못된 값 반영으로 동작이 바뀌는 상황을 피함 |
| 기록 | 오류 로그 기록 | 실패를 사후에 확인 가능하게 함 |
| 멱등 | 재적용 시 결과 동일 | 원인 해소 후 재적용이 단순해짐 |

### 4.4 서비스의 설정 읽기 모델

각 서비스는 기동 시 한 번 읽고, 이후에는 변경 이벤트를 받을 때만 다시 읽습니다. 폴링이 아니므로 변경이 없는 동안 추가 읽기가 없고, 설정 상태가 바뀌는 시점은 기동 시점과 이벤트 수신 시점 두 가지뿐입니다.

**주의점**

- **이벤트가 전달되지 않으면 재읽기가 일어나지 않습니다.** 전달 실패가 곧 설정 미반영으로 이어지므로 프록시와 동기화 실패 지표의 모니터링이 중요합니다.
- 기동 시 1회 읽기라는 성질은 재기동이 재동기화의 계기가 될 수 있음을 뜻합니다. 이를 운영 절차로 삼을지는 정해져 있지 않습니다(**확인 필요**).
- 기동 시 읽은 값이 어느 시점의 값인지(예: 검증 실패 상태에서 유지된 이전 설정인지)는 로그와 이력으로 확인해야 합니다.

### 4.5 배포 시 동작

배포 시 워커는 진행 중인 동기화를 마친 뒤 종료합니다. 동기화가 중간에 끊긴 상태로 남을 가능성이 줄고, 배포와 설정 반영이 겹칠 때의 불확실성도 줄어듭니다.

**주의점**

- 종료가 지연될 수 있으므로 **배포 소요 시간이 동기화 작업 시간에 영향을 받습니다.** 배포 창 계획에 반영하십시오.
- 최대 대기 시간과 강제 종료 조건은 주어지지 않았습니다(**확인 필요**).

## 5. 변경 관리와 이력

### 5.1 변경 창구 단일화

설정 변경은 관리 콘솔에서만 수행합니다. 변경 발생 지점이 특정되고, 이력이 누락 없이 남을 가능성이 높아집니다. 변경 지점이 분산되어 있던 `config.yaml` 복사 방식과의 핵심 차이입니다.

**주의점**

- 콘솔 외 경로(직접 테이블 수정, 파일 수정)가 기술적으로 가능한지, 가능하다면 차단·감지 방법은 주어지지 않았습니다(**확인 필요**). 원칙이 지켜지는지 확인할 수단을 함께 논의하십시오.
- 1단계 롤백 시 `config.yaml` 복사 방식으로 되돌아가므로(7절), 롤백 기간 동안 변경 창구가 일시적으로 달라집니다.

### 5.2 변경 이력: `settings_history`

| 항목 | 내용 |
| --- | --- |
| 저장 위치 | `settings_history` 테이블 |
| 보관 기간 | 90일 |
| 기록 대상 | 설정 변경 이력 |

설정 불일치가 의심될 때 언제 어떤 변경이 있었는지 확인하는 1차 자료이며, 1단계 원인 기록 작업의 기본 입력이 됩니다.

**주의점**

- **90일은 보관 상한입니다.** 그보다 오래된 변경은 조회할 수 없으므로, 장애 사후 분석 자료나 롤백 원인 기록처럼 장기 보관이 필요한 기록은 별도로 보존하십시오.
- 지난 분기 장애 4건처럼 과거 사례를 소급 분석하려면 보관 기간 경과 여부를 먼저 확인해야 합니다.
- 이력 항목의 스펙(변경자, 변경 전후 값, 시각 등)은 명시되어 있지 않습니다(**확인 필요**).

## 6. 전환 계획

### 6.1 단계 구성

## 7. 확인 및 모니터링

### 7.1 운영 첫날부터의 모니터링

| 확인 항목 | 관찰 대상 | 시작 시점 |
| --- | --- | --- |
| 동기화 실패 건수 | 동기화 작업의 실패 횟수 | 운영 적용 첫날 |
| 경보 발생 여부 | 경보가 실제로 발생하는지 | 운영 적용 첫날 |

두 항목은 2.3절의 현재 동작에서 도출됩니다. 현재 워커는 연결 단절 시 경보를 내지 않으므로, 전환 후에는 경보 경로가 살아 있는지 자체가 확인 대상입니다. "경보가 없다"는 관찰이 문제가 없다는 뜻인지, 경보 경로가 동작하지 않는다는 뜻인지 구분해야 합니다. 동기화 실패 건수는 재시도로 흡수되는 일시적 오류와 반복 실패를 구분하는 기초 자료입니다.

**주의점**

- 경보 임계값, 수집 주기, 알림 대상, 대응 절차는 주어지지 않았습니다(**확인 필요**). 운영 적용 전에 정해 두십시오.
- 오류 로그와 경보는 별개일 수 있으므로 두 경로를 모두 점검하십시오.

### 7.2 1단계 불일치 발견 시

1단계에서 불일치가 발견되면 `config.yaml` 복사 방식으로 롤백하고 원인을 기록합니다. 불일치 발견 여부가 1단계의 핵심 판정 기준이며, 조치는 **롤백과 원인 기록 두 가지**입니다. 하나만 수행하면 충분하지 않습니다. 절차는 8절에 있습니다.

### 7.3 2단계 전 설정값 비교

**절차(권장)**

1. 비교 기준을 `settings` 테이블의 값으로 고정합니다.
2. 12개 서비스가 실제 사용하는 설정값을 수집합니다.
3. 항목 단위로 대조해 일치·불일치를 기록합니다.
4. 불일치 항목이 서비스별 예외 설정에 해당하는지 확인합니다. 미결 사항 논의의 입력 자료가 됩니다.
5. 비교 결과를 2단계 진입 판단 근거로 씁니다.

**주의점**

- 이 비교는 **2단계 이전**의 선행 작업입니다. 2단계 적용과 동시에 진행하는 것이 아닙니다.
- 대상은 12개 전체입니다.
- 비교에서 나온 불일치가 곧 전환의 문제라고 단정할 수 없습니다. 기존 복사 방식에서 이미 있던 차이일 수 있으므로 원인을 구분해야 합니다.

## 8. 롤백 계획

### 8.1 트리거와 대상

| 항목 | 내용 |
| --- | --- |
| 적용 단계 | 1단계(결제·알림 / 스테이징) |
| 조건 | 불일치 발견 |
| 롤백 대상 방식 | `config.yaml` 복사 방식 |
| 부수 의무 | 원인 기록 |

### 8.2 절차

1. 불일치를 확인합니다. 어떤 항목에서, 어떤 서비스 간에 차이가 있는지 식별합니다.
2. `config.yaml` 복사 방식으로 되돌립니다. 각 서비스가 자체 `config.yaml`을 쓰는 상태가 됩니다.
3. 원인을 기록합니다. 기록은 조치의 일부이며 선택 사항이 아닙니다.
4. 기록된 원인을 2단계 진입 판단과 미결 사항 논의의 근거로 씁니다.

### 8.3 주의점

- 롤백 대상이 기존 방식이므로, 1단계 기간 동안 `config.yaml` 복사 방식이 사용 가능한 상태로 유지되는지 확인해 두십시오.
- 원인 기록의 보관 위치는 명시되어 있지 않습니다(**확인 필요**). `settings_history`는 90일 보관이므로 이력 테이블에만 의존하는 것은 권하기 어렵습니다.
- 2단계(운영)의 롤백 조건·절차는 주어지지 않았습니다(**미정**). 운영 적용 전에 정의하십시오.

## 10. 미결 사항

| 항목 | 내용 | 기한 | 상태 |
| --- | --- | --- | --- |
| 서비스별 예외 설정 처리 방식 | 2단계 전에 논의해 결정 | 2026-11-05 이전 | 미결 |

모든 설정을 `settings` 테이블에 단일하게 두는 구조에서는 서비스마다 값이 달라야 하는 설정의 처리가 쟁점이 됩니다. 문서에는 처리 방식이 정해져 있지 않고, 2단계 전에 결정해야 한다는 점만 명시되어 있습니다.

**논의 입력 자료**

- 12개 서비스 설정값 ↔ `settings` 비교 결과(7.3절) — 어떤 항목에서 차이가 있는지
- 1단계 불일치 원인 기록(8절) — 차이가 의도된 것인지, 전환 과정의 문제인지
- `schemas/settings.v2.json`의 정의 범위 — 예외 설정을 스키마 안에서 표현할 수 있는지

결정이 늦어지면 2단계 일정에 직접 영향을 줍니다. 논의 일정은 1단계 적용 직후로 잡으십시오. 결정이 필요한 사항이므로 본 문서에서는 특정 방안을 제시하지 않았습니다.
