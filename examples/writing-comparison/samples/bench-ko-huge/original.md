# 설정 동기화 서비스 전환 검토

**문서 상태:** 검토용 초안
**대상 범위:** 현재 개별 `config.yaml`을 사용하는 12개 서비스 전체
**전환 방식:** 중앙 `settings` 테이블 + 프록시 기반 변경 이벤트 전달 (서비스 코드 무수정)
**주요 일정:** 1단계 2026-10-15 스테이징 / 2단계 2026-11-05 운영

## 0. 요약 (Executive Summary)

이 문서는 현재 12개 서비스가 각자 복사해서 사용하고 있는 `config.yaml` 기반 설정 관리 방식을, 중앙 `settings` 테이블과 프록시 기반 이벤트 전달 구조로 전환하는 안건을 검토한 것입니다.

전환을 검토하게 된 직접적인 배경은 지난 분기에 발생한 **설정 불일치로 인한 장애 4건**이며, 이때의 **평균 복구 시간은 38분**이었습니다. 설정 파일이 서비스마다 복사본으로 존재하는 구조에서는 어느 복사본이 최신인지 판별하는 데 시간이 들고, 그만큼 복구가 지연될 여지가 있습니다.

전환 후 구조의 핵심은 다음 네 가지입니다.

1. **단일 저장 위치** — 모든 설정은 `settings` 테이블에 둡니다.
2. **단일 스키마 기준** — 설정의 형식 판정 기준은 `schemas/settings.v2.json` 파일입니다.
3. **프록시를 통한 전달** — 프록시가 설정 변경 이벤트를 각 서비스에 전달하며, **서비스 코드는 수정하지 않습니다.**
4. **단일 변경 창구** — 설정 변경은 관리 콘솔에서만 수행하고, 이력은 `settings_history` 테이블에 90일 보관합니다.

또한 현재 동기화 워커가 가진 두 가지 동작 특성(저장소 연결 단절 시 이전 값을 그대로 사용하고 경보를 내지 않음, 잘못된 형식의 값은 무시됨)은 전환 이후 **스키마 검증 실패 시 이전 설정 유지 + 오류 로그 기록**이라는 명시적 동작으로 대체됩니다.

미결 사항은 **서비스별 예외 설정 처리 방식**이며, 이는 2단계 진행 전에 논의하여 결정해야 합니다.

## 1. 현황 진단

### 1.1 배경: 현재 설정 관리 구조

현재 운영 중인 **12개 서비스는 각자 `config.yaml`을 복사해서 사용**하고 있습니다. 즉, 설정의 원본이 어디인지와 무관하게 실행 시점에는 서비스 수만큼의 복사본이 존재하는 형태입니다.

이 구조가 만들어 내는 성질을 정리하면 다음과 같습니다.

- **복사본의 수 = 서비스의 수**: 12개 서비스가 있으므로, 동일한 설정 항목에 대해 최대 12개의 값이 동시에 존재할 수 있습니다.
- **일치 여부는 보장되지 않고 확인되어야 함**: 복사 방식에서는 "모든 복사본이 같다"는 것이 구조적으로 보장되지 않으며, 별도로 비교해 확인해야 알 수 있습니다.
- **변경의 전파가 곧 복사 작업**: 설정을 바꾼다는 것은 여러 위치의 파일을 각각 갱신한다는 뜻이 됩니다.

### 1.2 근거: 지난 분기 지표

검토의 출발점이 되는 수치는 다음과 같습니다.

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 설정 불일치로 인한 장애 | **4건** | 지난 분기 집계 |
| 평균 복구 시간 | **38분** | 위 4건의 평균 |
| 설정 복사본이 존재하는 서비스 수 | **12개** | 전체 대상 서비스 |

이 표에서 읽을 수 있는 점은 다음과 같습니다.

- 장애의 원인이 "설정 불일치"로 분류되어 있다는 것은, **설정 값 자체의 오류와는 별개로 값이 서로 달라졌다는 사실이 원인으로 지목되었다**는 의미입니다. 복사본 구조에서 이러한 유형의 장애가 발생할 수 있다는 점이 실제 사례로 확인된 셈입니다.
- 평균 복구 시간 38분은 **단일 지표**이므로, 이 값만으로 개별 장애의 복구 시간 분포나 최댓값을 추정할 수는 없습니다. 즉 "모든 장애가 38분 내외였다"고 해석하지 않도록 주의해야 합니다.
- 전환 효과를 평가할 때에는 위 두 지표(건수·평균 복구 시간)를 비교 기준으로 삼는 것이 자연스럽습니다. 다만 목표 수치는 본 문서에 주어져 있지 않으므로, 필요하다면 별도로 합의해야 합니다.

### 1.3 현재 동기화 워커의 동작상 한계

현재 동기화 워커는 다음 두 가지 동작 특성을 가지고 있습니다.

1. **저장소 연결이 끊기면 이전 값을 그대로 사용하고, 경보를 내지 않습니다.**
2. **잘못된 형식의 값은 무시됩니다.**

두 특성이 실제 운영에서 어떤 결과로 이어지는지를 정리하면 다음과 같습니다.

| 상황 | 현재 워커의 동작 | 운영 관점의 함의 |
| --- | --- | --- |
| 저장소 연결 단절 | 이전 값 유지 | 서비스는 계속 동작하므로 표면적으로는 정상으로 보임 |
| 저장소 연결 단절 | **경보 없음** | 연결이 끊겼다는 사실이 운영자에게 전달되지 않음 |
| 잘못된 형식의 값 유입 | 해당 값 무시 | 무시되었다는 사실이 별도로 드러나지 않음 |

- **"조용한 실패"의 문제:** 위 두 동작의 공통점은, 실패가 발생해도 시스템이 멈추지 않고 외부로 신호를 내보내지 않는다는 점입니다. 결과적으로 문제가 감지되는 시점이 실제 발생 시점보다 늦어질 수 있습니다.
- **불일치와의 연결:** 일부 서비스에서만 값 갱신이 이루어지지 않는 상황은, 곧 서비스 간 설정 값이 달라지는 상황과 직결됩니다. 앞서 언급한 설정 불일치 장애를 다룰 때 이 동작 특성을 함께 고려해야 하는 이유입니다.
- **전환 설계의 요구사항:** 따라서 전환 후 구조에서는 최소한 **실패가 기록으로 남아야 한다**는 요구가 도출됩니다. 이는 아래 2.5절과 3.3절에서 다루는 "스키마 검증 실패 시 이전 설정 유지 + 오류 로그" 동작과 연결됩니다.

### 1.4 주의점

- 본 절의 진단은 제공된 사실에 한정됩니다. 4건의 장애가 각각 어떤 서비스에서, 어떤 설정 항목으로 인해 발생했는지는 본 문서에 포함되어 있지 않습니다. 원인 분석이 더 필요하다면 별도 자료를 확보해야 합니다.
- 현재 워커의 동작 특성은 "결함"으로 단정하기보다 **명시된 동작**으로 기술했습니다. 전환의 취지는 이 동작을 관측 가능한 형태로 바꾸는 데 있습니다.

## 2. 전환 후 목표 구조

### 2.1 개요

전환 후 구조는 아래와 같이 요약됩니다.

| 구성 요소 | 역할 |
| --- | --- |
| `settings` 테이블 | 모든 설정을 보관하는 단일 위치 |
| `schemas/settings.v2.json` | 설정 형식의 기준(스키마) 파일 |
| 프록시 | 설정 변경 이벤트를 각 서비스에 전달 |
| 각 서비스 | 기동 시 1회 설정 읽기, 이후 변경 이벤트 수신 시에만 재읽기 |
| 관리 콘솔 | 설정 변경의 유일한 창구 |
| `settings_history` 테이블 | 변경 이력 보관(90일) |
| 동기화 워커 | 동기화 작업 수행(멱등, 재시도, 배포 시 진행분 완료 후 종료) |

### 2.2 단일 저장 위치: `settings` 테이블

**배경.** 복사본이 여러 개 존재하는 구조에서는 "무엇이 정답인가"를 판정할 기준점이 없습니다. 전환 후에는 모든 설정을 `settings` 테이블에 두어 이 기준점을 하나로 만듭니다.

**근거.** 저장 위치가 하나이면 다음이 따라옵니다.

- 값 비교의 기준이 명확해집니다. 어떤 서비스의 값이 기준과 다른지 확인할 대상이 정해집니다.
- 변경 지점이 좁아집니다. 값이 바뀌는 위치가 한 곳이므로 추적 범위가 줄어듭니다.
- 2단계 전 점검 항목인 "12개 서비스 설정값을 `settings` 테이블과 비교"가 성립하려면 애초에 비교 기준이 되는 단일 테이블이 필요합니다.

**주의점.**

- 저장 위치를 하나로 모으는 것과, 각 서비스가 그 값을 실제로 반영했는지는 별개의 문제입니다. 반영 여부는 별도 확인(6절)을 통해 검증해야 합니다.
- 서비스별로 값이 달라야 하는 설정이 있을 수 있으며, 이 처리 방식은 **미결 사항**입니다(9절 참조).

### 2.3 단일 기준 스키마: `schemas/settings.v2.json`

**배경.** 현재 워커는 잘못된 형식의 값을 무시합니다. 즉 "무엇이 올바른 형식인가"에 대한 판정은 이루어지고 있으나, 그 판정 결과가 외부로 드러나지 않는 형태입니다.

**근거.** 전환 후에는 `schemas/settings.v2.json` 파일을 스키마의 기준으로 삼습니다. 기준 파일이 명시되면 다음이 가능해집니다.

- 검증 통과/실패의 판단 근거가 파일 하나로 특정됩니다.
- 스키마가 변경될 경우, 변경 대상 파일이 명확합니다.
- 검증 실패 시의 동작(2.5절)을 정의할 대상이 분명해집니다.

**절차(권장).**

1. 설정 변경 요청이 관리 콘솔을 통해 들어옵니다.
2. 대상 값이 `schemas/settings.v2.json` 기준으로 검증됩니다.
3. 검증을 통과하면 반영, 실패하면 이전 설정 유지 및 오류 로그 기록.

**주의점.**

- 스키마 파일의 버전 관리·변경 승인 절차는 본 문서에 주어지지 않았습니다. 파일명이 `v2`인 점으로 미루어 버전 개념이 존재할 가능성이 있으나, 이전 버전과의 관계나 마이그레이션 방식은 확인이 필요합니다.
- 스키마에 정의되지 않은 항목을 어떻게 다룰지는 **서비스별 예외 설정 처리 방식**(미결)과 겹칠 수 있으므로, 2단계 전 논의에서 함께 다루는 것이 좋겠습니다.

### 2.4 전달 경로: 프록시 기반 이벤트 전달

**배경.** 전환 시 가장 큰 부담은 대개 애플리케이션 코드 변경입니다. 12개 서비스 각각에 설정 구독 로직을 넣는다면 개발·검증 비용이 서비스 수만큼 늘어납니다.

**근거.** 본 전환에서는 **프록시가 설정 변경 이벤트를 각 서비스에 전달**하며, **서비스 코드는 수정하지 않습니다.** 이 선택의 의미는 다음과 같습니다.

| 항목 | 프록시 방식의 성격 |
| --- | --- |
| 서비스 코드 변경 | 없음 |
| 이벤트 전달 주체 | 프록시 |
| 전환 단위 | 서비스별 코드가 아닌 전달 계층 |
| 회귀 위험의 위치 | 서비스 내부 로직보다는 전달 계층 쪽 |

**주의점.**

- 서비스 코드를 고치지 않는다는 것은 곧 **프록시가 단일 경유 지점이 된다**는 뜻이기도 합니다. 전달 계층의 동작이 전체 서비스에 영향을 미칠 수 있으므로, 단계적 적용(5절)과 모니터링(6절)이 중요합니다.
- 프록시의 배치 형태, 이벤트 프로토콜, 실패 시 전달 재시도 정책의 세부는 본 문서에 명시되어 있지 않습니다. 재시도와 관련해서는 "일시적 연결 오류는 재시도로 처리한다"는 원칙(3.2절)이 주어져 있습니다.

### 2.5 검증 실패 시 동작

전환 후에는 스키마 검증 실패 시 다음과 같이 동작합니다.

- **이전 설정을 유지합니다.**
- **오류 로그를 남깁니다.**

이를 현재 동작과 비교하면 다음과 같습니다.

| 상황 | 현재 | 전환 후 |
| --- | --- | --- |
| 잘못된 형식의 값 | 무시됨 | 스키마 검증 실패 → 이전 설정 유지 + 오류 로그 |
| 저장소 연결 단절 | 이전 값 유지, 경보 없음 | (아래 주의점 참조) |

**주의점.**

- "이전 설정을 유지한다"는 점은 현재와 동일한 방향이지만, **오류 로그가 남는다는 점이 결정적인 차이**입니다. 문제의 존재가 기록으로 드러나므로, 사후 확인과 원인 추적이 가능해집니다.
- 다만 **오류 로그와 경보(alert)는 구분해야 합니다.** 본 문서에 주어진 사실은 "오류 로그를 남긴다"이며, 로그가 자동으로 경보로 이어지는지는 명시되어 있지 않습니다. 운영 적용 첫날부터 **경보 발생 여부를 모니터링**하는 항목(6절)이 있으므로, 로그–경보 연결 여부는 실제 확인을 통해 점검하는 것이 좋겠습니다.

## 3. 동기화 동작 원칙

### 3.1 멱등성

**정의.** 동기화 작업은 **같은 설정을 여러 번 적용해도 결과가 같습니다.**

**근거와 효과.**

- **재시도가 안전해집니다.** 같은 작업을 다시 수행해도 결과가 달라지지 않으므로, 재시도를 부작용 걱정 없이 사용할 수 있습니다.
- **중복 이벤트에 견딥니다.** 동일한 변경 이벤트가 둘 이상 전달되더라도 최종 상태가 동일합니다.
- **복구 절차가 단순해집니다.** "다시 한 번 적용해 본다"가 유효한 대응 수단이 됩니다.

**주의점.**

- 멱등성은 "결과가 같다"는 보장이며, **적용이 항상 성공한다는 보장은 아닙니다.** 검증 실패나 연결 오류는 별도의 경로로 처리됩니다(2.5절, 3.2절).

### 3.2 재시도

**정의.** **일시적 연결 오류는 재시도로 처리합니다.**

**절차(원칙).**

1. 동기화 작업 중 연결 오류가 발생합니다.
2. 해당 오류가 일시적인 성격이라면 재시도합니다.
3. 멱등성(3.1절)에 의해 재시도로 인한 결과 변화는 없습니다.

**주의점.**

- **재시도 횟수, 간격, 백오프 정책, 최종 실패 시 처리**는 본 문서에 주어지지 않았습니다. 실제 구현·설정 시 별도 합의가 필요합니다.
- 재시도로도 해결되지 않는 지속적 장애와 일시적 오류의 구분 기준 또한 명시되어 있지 않습니다. 운영 적용 첫날부터 수집하는 **동기화 실패 건수**(6절)가 이 구분을 판단하는 데 참고 자료가 될 수 있습니다.
- 현재 워커가 연결 단절 시 경보를 내지 않는다는 점(1.3절)을 고려하면, 재시도 처리와 실패 가시화를 **함께** 확인하는 것이 바람직합니다.

### 3.3 검증 실패 처리

앞서 2.5절에서 설명한 바와 같이, 스키마 검증 실패 시에는 이전 설정을 유지하고 오류 로그를 남깁니다. 동작 원칙 관점에서 정리하면 다음과 같습니다.

| 원칙 | 내용 | 의도 |
| --- | --- | --- |
| 안전 우선 | 검증 실패 시 이전 설정 유지 | 잘못된 값이 반영되어 동작이 바뀌는 상황을 피함 |
| 기록 남김 | 오류 로그 기록 | 실패가 사후에 확인 가능하도록 함 |
| 멱등 | 재적용 시 결과 동일 | 원인 해소 후 재적용이 단순해짐 |

### 3.4 서비스의 설정 읽기 모델

**정의.** 각 서비스는 **기동 시 설정을 한 번 읽고, 이후에는 변경 이벤트를 받을 때만 다시 읽습니다.**

**근거와 효과.**

- 주기적 폴링이 아니라 **이벤트 기반 재읽기**이므로, 변경이 없는 동안에는 추가 읽기가 발생하지 않습니다.
- 서비스의 설정 상태가 언제 바뀌는지가 명확합니다. 즉 **기동 시점** 또는 **변경 이벤트 수신 시점** 두 가지뿐입니다.

**주의점 — 이 모델에서 특히 유의해야 할 점입니다.**

- **이벤트가 전달되지 않으면 서비스는 재읽기를 하지 않습니다.** 이벤트 전달 실패가 곧 설정 미반영으로 이어질 수 있으므로, 전달 계층(프록시)과 동기화 실패 지표의 모니터링이 중요합니다.
- 서비스가 **기동할 때 한 번 읽는다**는 점은, 재기동이 설정 재동기화의 계기가 될 수 있음을 의미합니다. 다만 이를 운영 절차로 삼을지는 본 문서에 정해져 있지 않습니다.
- 기동 시점에 읽은 값이 어떤 시점의 값인지(예: 검증 실패 상태에서 유지되던 이전 설정인지)에 대한 해석은 로그와 이력(4절)을 통해 확인해야 합니다.

### 3.5 배포 시 동작

**정의.** 배포 시 **워커는 진행 중인 동기화를 마친 뒤 종료됩니다.**

**효과.**

- 동기화가 중간에 끊긴 상태로 남을 가능성을 줄입니다.
- 배포 작업과 설정 반영 작업이 겹칠 때의 불확실성이 줄어듭니다.

**주의점.**

- 진행 중인 동기화를 마칠 때까지 종료가 지연될 수 있으므로, **배포 소요 시간이 동기화 작업 시간에 영향을 받을 수 있습니다.** 배포 창(window)을 계획할 때 이 점을 고려하는 것이 좋겠습니다.
- 최대 대기 시간이나 강제 종료 조건은 본 문서에 명시되어 있지 않습니다.

## 4. 변경 관리와 이력

### 4.1 변경 창구의 단일화

**정의.** **설정 변경은 관리 콘솔에서만 수행합니다.**

**근거.**

- 변경 경로가 하나이면, 변경이 발생할 수 있는 지점이 특정됩니다.
- 이력 기록(4.2절)이 누락 없이 남을 가능성이 높아집니다.
- 기존의 "각자 `config.yaml`을 복사"하는 방식과 대비되는 핵심 차이이기도 합니다. 복사 방식에서는 변경 지점이 분산되어 있었습니다.

**주의점.**

- 관리 콘솔 외 경로(예: 직접 테이블 수정, 파일 수정)가 기술적으로 가능한지 여부와, 가능하다면 이를 어떻게 차단하거나 감지할지는 본 문서에 주어져 있지 않습니다. 원칙이 실제로 지켜지는지 확인할 수단을 검토 과정에서 함께 논의하시길 권합니다.
- 1단계 롤백 시에는 `config.yaml` 복사 방식으로 되돌아가게 되므로(7절), 롤백 기간 동안에는 변경 창구가 일시적으로 달라진다는 점을 인지해야 합니다.

### 4.2 변경 이력: `settings_history` 테이블

**정의.** 변경 이력은 **`settings_history` 테이블에 90일 보관**합니다.

| 항목 | 내용 |
| --- | --- |
| 저장 위치 | `settings_history` 테이블 |
| 보관 기간 | 90일 |
| 기록 대상 | 설정 변경 이력 |

**활용 관점.**

- 설정 불일치가 의심될 때, 언제 어떤 변경이 있었는지 확인하는 1차 자료가 됩니다.
- 1단계에서 불일치가 발견될 경우 **원인을 기록**해야 하므로(6절·7절), 이력 조회가 원인 규명 작업의 기본 입력이 됩니다.

**주의점.**

- **90일이라는 보관 기간은 상한입니다.** 90일보다 오래된 변경은 이 테이블에서 조회할 수 없으므로, 장기 보관이 필요한 기록(예: 장애 사후 분석 자료, 롤백 원인 기록)은 **별도로 보존**하는 편이 안전합니다.
- 지난 분기 장애 4건과 같이 과거 사례를 소급 분석하려는 경우, 보관 기간 경과 여부를 먼저 확인해야 합니다.
- 이력에 기록되는 항목의 구체적 스펙(변경자, 변경 전/후 값, 시각 등)은 본 문서에 명시되어 있지 않습니다.

## 6. 확인 및 모니터링 항목

### 6.1 운영 적용 첫날부터의 모니터링

**정의.** **운영 적용 첫날부터 동기화 실패 건수와 경보 발생 여부를 모니터링**합니다.

| 확인 항목 | 관찰 대상 | 시작 시점 |
| --- | --- | --- |
| 동기화 실패 건수 | 동기화 작업의 실패 발생 횟수 | 운영 적용 첫날 |
| 경보 발생 여부 | 경보가 실제로 발생하는지 | 운영 적용 첫날 |

**근거.** 이 두 항목이 선정된 배경은 1.3절의 현재 워커 동작과 직접 연결됩니다.

- 현재 워커는 저장소 연결 단절 시 **경보를 내지 않습니다.** 따라서 전환 후 **경보가 실제로 발생하는지** 자체가 확인 대상이 됩니다. "경보가 없다"는 관찰이 "문제가 없다"를 의미하는지, 아니면 "경보 경로가 동작하지 않는다"를 의미하는지 구분할 필요가 있기 때문입니다.
- 동기화 실패 건수는 재시도(3.2절)로 흡수되는 일시적 오류와, 반복적으로 실패하는 사안을 구분하는 기초 자료가 됩니다.

**주의점.**

- **경보 임계값, 수집 주기, 알림 대상, 대응 절차**는 본 문서에 주어지지 않았습니다. 운영 적용 전에 정해 두는 것이 바람직합니다.
- 오류 로그(2.5절)와 경보는 별개 개념일 수 있으므로, 두 경로가 모두 살아 있는지 점검을 권합니다.

### 6.2 1단계 불일치 발견 시 조치

**정의.** **1단계에서 불일치가 발견되면 `config.yaml` 복사 방식으로 롤백하고 원인을 기록**합니다.

절차는 7절에서 상세히 다룹니다. 확인 항목 관점에서 요점만 정리하면 다음과 같습니다.

- 불일치 **발견 여부**가 1단계의 핵심 판정 기준입니다.
- 발견 시 조치는 **롤백**과 **원인 기록** 두 가지이며, 둘 중 하나만 수행해서는 충분하지 않습니다.

### 6.3 2단계 전 설정값 비교

**정의.** **2단계 전에 12개 서비스의 설정값을 `settings` 테이블과 비교**합니다.

**절차(권장).**

1. 비교 기준을 `settings` 테이블의 값으로 고정합니다.
2. 12개 서비스 각각이 실제로 사용하는 설정값을 수집합니다.
3. 항목 단위로 대조하여 일치/불일치를 기록합니다.
4. 불일치가 있는 경우, 해당 항목이 **서비스별 예외 설정에 해당하는지** 확인합니다. 이는 미결 사항(9절)과 직결되므로, 결정 논의의 입력 자료로 활용할 수 있습니다.
5. 비교 결과를 2단계 진입 판단의 근거로 사용합니다.

**주의점.**

- 이 비교는 **2단계 이전**에 수행하는 선행 작업입니다. 2단계 적용과 동시에 진행하는 것이 아니라는 점에 유의해 주십시오.
- 대상은 **12개 전체**입니다(5.3절 주의점 참조).
- 비교 결과에서 나타난 불일치가 곧 전환의 문제라고 단정할 수는 없습니다. 기존 복사 방식에서 이미 존재하던 차이일 수도 있으므로, 원인 구분이 필요합니다.

## 7. 롤백 계획

### 7.1 롤백 트리거

**1단계에서 불일치가 발견되는 경우**가 명시된 롤백 조건입니다.

| 항목 | 내용 |
| --- | --- |
| 적용 단계 | 1단계 (결제, 알림 / 스테이징) |

| 롤백 대상 방식 | **`config.yaml` 복사 방식** |
| 부수 의무 | **원인 기록** |

### 7.2 롤백 절차(원칙)

1. **불일치 발견을 확인합니다.** 어떤 설정 항목에서, 어떤 서비스 간에 차이가 있는지 식별합니다.
2. **`config.yaml` 복사 방식으로 되돌립니다.** 전환 전 방식으로 복귀하는 것이므로, 각 서비스가 자체 `config.yaml`을 사용하는 상태가 됩니다.
3. **원인을 기록합니다.** 기록은 조치의 일부이며 선택 사항이 아닙니다.
4. 기록된 원인을 2단계 진입 판단 및 미결 사항 논의(9절)의 근거로 활용합니다.

### 7.3 주의점

- 롤백 대상이 **기존 방식(`config.yaml` 복사)**이라는 점은, 전환 이전 구조가 롤백 시점까지 사용 가능한 상태로 유지되어야 함을 시사합니다. 1단계 기간 동안 기존 방식의 가용성을 확인해 두는 것이 안전합니다.
- **원인 기록의 보관 위치**는 본 문서에 명시되어 있지 않습니다. `settings_history`는 변경 이력을 90일 보관하는 테이블이므로, 원인 기록을 이력 테이블에만 의존하는 것은 보관 기간 측면에서 권하기 어렵습니다.
- 2단계(운영)에 대한 롤백 조건·절차는 본 문서에 주어져 있지 않습니다. 운영 적용 전에 별도로 정의하는 것을 권합니다.

## 9. 미결 사항

| 항목 | 내용 | 기한 | 상태 |
| --- | --- | --- | --- |
| 서비스별 예외 설정 처리 방식 | **2단계 전에 논의해 결정해야 함** | 2026-11-05 이전 | **미결** |

**배경.** 모든 설정을 `settings` 테이블에 단일하게 두는 구조에서는, 서비스마다 값이 달라야 하는 설정을 어떻게 다룰지가 자연스럽게 쟁점이 됩니다. 본 문서에는 이 처리 방식이 정해져 있지 않으며, **2단계 전에 논의해 결정해야 한다**는 점만 명시되어 있습니다.

**논의 시 참고할 수 있는 입력 자료.**

- 6.3절의 **12개 서비스 설정값 ↔ `settings` 테이블 비교 결과** — 실제로 어떤 항목에서 서비스 간 차이가 존재하는지를 보여 줍니다.
- 1단계에서 불일치가 발견된 경우의 **원인 기록**(7절) — 차이가 의도된 것인지, 전환 과정의 문제인지 구분하는 데 도움이 됩니다.
- `schemas/settings.v2.json`의 정의 범위 — 예외 설정이 스키마 안에서 표현 가능한지 여부와 연결됩니다.

**주의점.**

- 결정이 늦어지면 2단계 일정에 직접적인 영향을 줍니다. 논의 일정을 1단계 적용 이후 가급적 이른 시점에 잡아 두시길 권합니다.
- 이 항목은 **결정이 필요한 사항**이므로, 본 문서에서는 특정 방안을 제시하지 않았습니다.

- 동기화는 멱등하고 일시적 연결 오류는 재시도로 처리되므로, 재적용 중심의 단순한 복구 전략을 취할 수 있습니다.
- 일정은 **1단계 2026-10-15 스테이징(결제·알림)**, **2단계 2026-11-05 운영(나머지 10개)**이며, 2단계 전에 **12개 서비스 설정값 비교**와 **서비스별 예외 설정 처리 방식 결정**이 반드시 선행되어야 합니다.

남은 미결 사항은 **서비스별 예외 설정 처리 방식** 하나이며, 이 결정이 2단계 일정의 실질적인 선행 조건이라는 점을 다시 한 번 강조드립니다.
