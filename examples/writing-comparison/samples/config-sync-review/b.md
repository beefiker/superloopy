# 설정 동기화 서비스 전환 검토

**결론:** 12개 서비스가 각자 복사해 쓰는 `config.yaml`을 `settings` 테이블 하나로 옮겨야 합니다.

**근거:** 지난 분기 설정 불일치 장애 4건, 평균 복구 시간 38분. 설정 파일은 서비스마다 복사되고 불일치는 매주 발견되며 복구 시간은 점점 길어지고 있습니다.

## 전환 방식

1. 모든 서비스가 설정을 `settings` 테이블에서만 읽게 합니다. 스키마는 `schemas/settings.v2.json` 하나로 고정합니다.
2. 각 서비스의 설정 파일과 복사 스크립트를 없앱니다.
3. 프록시가 설정 변경 이벤트를 서비스 코드 수정 없이 각 서비스에 전달하게 합니다.
4. 동기화 작업은 멱등성이 있어 같은 설정을 여러 번 적용해도 결과가 같습니다. 일시적인 연결 오류는 재시도로 대응할 수 있습니다.

설정 변경은 관리 콘솔에서만 합니다. 변경 이력은 `settings_history` 테이블에 90일 동안 보관합니다. 각 서비스는 기동할 때 설정을 한 번 읽습니다. 그 뒤에는 변경 이벤트를 받을 때만 다시 읽습니다.

| 단계 | 대상 | 일정 |
| --- | --- | --- |
| 1단계 | 결제, 알림 서비스 | 2026-10-15 스테이징 |
| 2단계 | 나머지 10개 서비스 | 2026-11-05 운영 |

## 실패 처리

- 현재: 저장소 연결이 끊기면 워커는 이전 값을 그대로 쓰고 경보를 내지 않습니다. 잘못된 형식의 설정값은 무시됩니다.
- 전환 후: 스키마 검증에 실패하면 이전 설정을 유지하고 오류 로그를 남깁니다. 배포 시 워커는 진행 중인 동기화를 마친 뒤 종료됩니다.
- 원칙: 속도보다 정확성. 문제는 도구가 아니라 절차입니다.

## 확인 항목

- [모니터링] 운영 적용 첫날부터 동기화 실패 건수와 경보 발생 여부를 대시보드에서 확인합니다.
- [롤백] 1단계에서 불일치가 발견되면 `config.yaml` 복사 방식으로 되돌리고 원인을 기록합니다.
- [검증] 2단계 전에 12개 서비스의 설정값을 `settings` 테이블과 비교합니다.

**미결:** 서비스별 예외 설정 처리 방식. 2단계 전에 결정해야 합니다.

**다음 행동:** 서비스별 예외 설정 논의 일정을 2단계 전으로 잡습니다.
