# LLM 위키 도입 검토

우리 회사(BEE)는 개발자 30여 명이 대형 프로젝트 3개를 나누어 맡고 있으며, 프로젝트마다 10명 이상이 참여하고 있습니다. AI 도구를 적극적으로 사용하는 개발자도 자기 프로젝트 밖의 배경지식이 없어 다른 프로젝트 작업에서는 에이전트가 내놓은 결과를 확신하지 못합니다. 실제로 다른 팀 저장소를 수정해야 하는 작업은 담당자에게 질문이 몰리고, 답을 기다리는 동안 작업이 멈추는 일이 반복됩니다. 이 문제를 해결할 방안으로 LLM 위키 도입을 검토했습니다.

## LLM 위키란 무엇인가

LLM 위키는 사람이 읽는 위키가 아니라 LLM과 코딩 에이전트가 컨텍스트로 읽도록 정리한 사내 지식 저장소입니다. 실무에서는 색인 중심의 마크다운 문서 모음, 저장소마다 두는 AGENTS.md 안내 문서, 기존 위키에 검색을 붙이는 RAG, 문서 시스템을 그대로 연결하는 MCP 서버라는 네 가지 형태로 구현됩니다. 네 가지는 서로 배타적이지 않으며, 공개된 성공 사례 대부분은 저장소별 안내 문서와 검색 계층을 함께 쓰는 혼합 구성입니다. 어떤 형태를 선택하든 여러 사례에서 확인된 핵심은 검색 기술이 아니라 문서의 품질과 최신성입니다.

## 구축 절차

1. 프로젝트마다 구조, 규칙, 주의점을 담은 AGENTS.md를 작성하고 200줄 이하로 유지합니다. 자동 생성 초안은 사람이 검토한 뒤에만 반영합니다.
2. 프로젝트를 가로지르는 아키텍처와 용어는 색인 문서 하나에 모으고, 모듈마다 문서 한 장을 둡니다.
3. 기존 위키를 연결하기 전에 문서 접근 권한부터 정리합니다. 검색 계층은 각 사용자가 권한상 볼 수 있는 모든 문서를 실제로 보이게 만들기 때문입니다.
4. 기존 위키 문서는 옮기지 않고 검색이나 MCP로 연결합니다.
5. 문서마다 담당자를 지정하고, 코드가 바뀌면 관련 문서를 검토하도록 CI에서 확인합니다.
6. 도입 전에 실제 질문 20~30개로 평가 세트를 만들어 두고, 같은 질문으로 개선 여부를 측정합니다.
7. 에이전트가 잘못한 일은 코드만 고치지 말고, 해당 프로젝트의 AGENTS.md에 다시 하지 말라는 규칙 한 줄로 남깁니다.

## 기대 효과

가장 검증된 효과는 다른 프로젝트 질문에 에이전트가 출처와 함께 답하는 교차 프로젝트 질의응답입니다. 공개된 사례에서는 지원 문의 처리와 온보딩에서 효과가 가장 먼저 나타났습니다. 신규 입사자의 적응 기간이 약 20% 줄었다는 보고와 사내 질의응답 봇이 수만 건의 질문을 처리해 담당자의 반복 응대 시간을 줄였다는 보고가 있습니다.

에이전트 작업의 정확도도 개선됩니다. 잘 정리된 색인 문서를 넣자 익숙하지 않은 프레임워크 작업의 평가 통과율이 53%에서 100%로 올라갔다는 평가가 공개되어 있고, 대형 저장소에서는 에이전트가 컨텍스트 창의 절반을 검색에 낭비하는 문제가 줄어듭니다.

마지막으로 문서화 문화 자체가 개선되는 효과가 있습니다. 에이전트가 읽는다는 사실은 문서를 쓸 즉각적인 이유가 되고, 색인 갱신이나 상호 참조 정리처럼 사람이 미루던 반복 작업은 에이전트에게 맡길 수 있습니다. 효과는 답변 채택률, 중복 질문 수, 온보딩 기간처럼 측정 가능한 지표로 확인해야 하며, 도입 자체를 성과로 보고해서는 안 됩니다.

## 한계와 위험

- 방치된 문서는 없는 문서보다 위험합니다. 사람은 오래된 문서를 의심하지만 에이전트는 오래된 내용을 그대로 확신하는 답으로 내놓고, 폐기된 패턴을 새 코드에 복제해 다음 에이전트가 참고할 낡은 사례를 늘립니다.
- 검색 실패는 사라지지 않습니다. 기존 위키를 통째로 물린 봇은 첫 버전에서 답변의 절반가량만 유용하다는 평가를 받았고, 상용 검색 제품에서도 17~33%의 오답률이 측정된 사례가 있습니다. 표, 코드, 도메인 용어가 많은 문서일수록 실패가 잦습니다.
- 권한 문제는 도입 뒤에 드러납니다. 평균적인 조직에서 수십만 건의 문서가 필요 이상으로 공유되어 있다는 조사가 있으며, 질문 한 번으로 그 전부가 노출될 수 있습니다. 메일 한 통의 주입 공격으로 사내 문서가 새어 나간 사고와, 비공개로 돌린 저장소가 검색 색인에 남아 있던 사고도 이미 보고됐습니다.
- 유지 부담은 도구가 대신 짊어져 주지 않습니다. 담당자가 없으면 다시 낡은 위키로 돌아가고, 자동으로 생성해 둔 안내 문서는 추론 비용만 20% 늘리고 효과가 없었다는 평가도 있습니다. 에이전트가 실패한 작업에서 드러난 내용만 문서에 추가하는 규율이 필요합니다.
- 비용은 토큰보다 운영에서 늘어납니다. 도입 조직의 절반 이상이 예산을 초과할 것이라는 전망이 있고, 데이터 정리에 전체 비용의 30~50%가 들어간다는 집계도 있으며, 비용 계산이 5~10배까지 어긋난 사례도 보고됐습니다.
- 정착은 저절로 되지 않습니다. 사내 검색을 도입한 조직에서 실사용률이 20~40%에 머문 사례가 보고되어 있고, 초기에 틀린 답을 겪은 사용자는 다시 돌아오지 않는 경향이 있습니다.

LLM 위키가 해결하지 못하는 문제도 분명합니다. 적히지 않은 지식은 답할 수 없고, 잘못 기록된 결정은 그대로 잘못된 답의 근거가 되며, 에이전트 결과물에 대한 사람의 검토는 여전히 필요합니다. 사용자 3분의 2가 AI 답변을 검증하지 않고 쓴다는 조사 결과를 감안하면, 출처 표시와 정답률 공개는 선택이 아니라 신뢰를 지키는 장치입니다.

> 문서를 관리하지 않은 채 도구만 얹으면, AI는 우리가 쌓아 둔 것을 그대로 되풀이할 뿐이다.

문서를 선별하고 담당자를 두어 관리한 팀은 효과를 얻었고, 기존 위키를 그대로 물린 팀은 절반만 맞는 봇과 신뢰 문제를 얻었다는 것이 공통된 평가입니다.

## 도입 조직의 실전 수칙

공개된 사례에서 거듭 확인되는 실전 수칙입니다.

- 실수를 규칙으로 바꿉니다. 클로드 코드를 만든 보리스 체르니의 팀은 리뷰어가 에이전트의 잘못을 잡을 때마다 그 교훈을 공유 CLAUDE.md에 한 줄로 남기며, 같은 습관을 여러 실무자가 각자 만들어 냈을 만큼 보편적인 수칙입니다.
- 문서 추가는 실패가 증명할 때만 합니다. 에이전트가 작업에 실패하면 그때 한 줄을 더하고, 되돌린 뒤 같은 작업을 다시 시켜 그 줄이 실제로 문제를 고쳤는지 확인합니다. 안내 문서가 200줄을 넘으면 잘못 쓰고 있다는 신호로 봅니다.
- 비자명한 작업은 계획 파일부터 만듭니다. 고스티를 만든 미첼 해시모토는 에이전트와 대화로 계획을 다듬어 파일로 저장하고, 세션이 바뀌어도 같은 계획을 다시 읽게 합니다.
- 답변마다 피드백 버튼을 답니다. 우버는 슬랙 답변에 도움 여부 버튼을 달아 클릭을 데이터 파이프라인으로 흘려보내고, 전문가가 만든 골든 질문 100여 개를 LLM 심판이 채점해 기준을 넘긴 채널에만 봇을 배포합니다.
- 문서 갱신 신호를 리뷰어에게 맡깁니다. 클라우드플레어는 AI 코드 리뷰어가 저장소 변화를 보고 안내 문서 갱신이 필요하다고 표시하게 했고, 초안은 모델이 쓰되 승인은 팀이 병합 요청으로 합니다.
- 검증된 문서만 색인합니다. 링크드인은 도메인 전문가가 인증한 테이블과 예시 쿼리만 봇에 물리고, 폐기 표시가 붙은 테이블은 자동으로 뺍니다.
- 운영 지식을 적습니다. 플라스크를 만든 아르민 로나허는 '디버그 모드에서는 메일이 로그로 찍힌다' 같은 운영 사실을 적어 두는 편이 스타일 지침보다 에이전트를 실제로 움직인다고 정리했습니다.

안내 문서의 길이에는 정답이 없습니다. 800줄짜리 문서를 에이전트가 직접 갱신하게 두고 사람은 가지치기만 하는 실무자가 있는가 하면, 모델이 앞서 나가지 못하도록 컨텍스트를 일부러 굶기는 실무자도 있습니다. 어느 쪽이든 문서를 평가로 검증한다는 공통점이 있습니다.

## 제안

프로젝트 1개를 대상으로 3개월 시험 도입을 제안합니다. 기업 상당수가 AI 프로젝트 대부분을 검증 단계에서 접는다는 조사가 이어지는 만큼, 전면 도입 대신 중단 기준이 있는 시험 도입을 택했습니다. 첫 달에는 AGENTS.md 작성과 색인 문서 정리, 권한 점검, 평가 세트 작성을 하고, 이후 두 달 동안은 다른 프로젝트 개발자가 에이전트로 질문했을 때 출처가 있는 답을 받는지 매달 측정합니다. 판정 기준은 시작 전에 합의합니다. 평가 세트 정답률과 답변 채택률이 첫 달보다 오르지 않거나 문서 담당자 지정을 유지할 수 없으면, 확대하지 않고 종료합니다.
